# دليل التشغيل والطوارئ — `pharmacy-web`

> يمثّل هذا الملف ما يمكن للواجهة أن تضمنه. البنود المتعلقة بقاعدة البيانات أو الخادم
> موضوعة هنا كإجراءات يجب تنفيذها من فريق الخادم، لا كادعاءات إنجاز.

## 1. قبل كل نشر (5 دقائق)

```bash
npm ci
npm run verify            # typecheck + lint + tests + boundaries + secrets + audit + build
node scripts/verify-deployment.mjs https://<الواجهة> https://<الـ API>
```

`verify-deployment.mjs` يفشل عند: غياب ترويسة أمنية، CSP لا يسمح بأصل الـ API،
أو CORS لا يسمح بمنشأ الواجهة، أو `/api/v1` غير موصول (يعيد HTML).
**نجاح `next build` لا يكفي** — هذا السكربت هو الفرق بين «يبني» و«يعمل».

## 2. متغيرات البيئة

| المتغير | إلزامي | الغرض |
|---|---|---|
| `NEXT_PUBLIC_API_BASE_URL` | لا (افتراضي `/api/v1`) | عنوان الـ API كما يراه المتصفح؛ يُضاف أصله تلقائيًا إلى CSP |
| `API_PROXY_TARGET` | لا | rewrite محلي/وقت البناء فقط |
| `CSP_REPORT_URI` | لا | تجميع انتهاكات CSP قبل تشديد السياسة |
| `NEXT_PUBLIC_ERROR_ENDPOINT` | لا | استقبال تقارير الأخطاء (بلا بيانات حساسة) |
| `NEXT_PUBLIC_BUILD_ID` | لا | تمييز الإصدار في تقارير المراقبة |

## 3. المراقبة

- **أخطاء الواجهة**: `reportError` في `src/lib/monitoring.ts`. ترسل `kind/route/status/code/requestId/digest/release` فقط.
  لا تُرسل توكنات أو أسماء عملاء أو مبالغ. بلا `NEXT_PUBLIC_ERROR_ENDPOINT` تبقى في الطرفية.
- **requestId**: يُقرأ من ترويسة `x-request-id` ويُحفظ في `ApiException`. اطلبه من المستخدم عند أي شكوى — يربط الشاشة بطلب الخادم.
- **لوحة تحكم مقترحة**: معدل `NETWORK_TIMEOUT` و`429` و`DUR_BLOCK` يوميًا + كل `BAD_RESPONSE` (يعني تعارض عقد مع الـ API).

## 4. النسخ الاحتياطي والاسترجاع (مسؤولية الخادم/قاعدة البيانات)

الواجهة لا تحتوي بيانات مالية؛ كل شيء في الـ API. لذلك:

1. **قبل أي إطلاق**: نفّذ استرجاعًا تجريبيًا لقاعدة البيانات على بيئة منفصلة، وسجّل زمن الاسترجاع (RTO) والفاقد المقبول (RPO).
2. **نسخ يومية** + نقطة استرجاع قبل كل ترحيل (migration). النسخ غير المُجرَّبة = لا نسخ.
3. **بعد الاسترجاع**: تحقق من تطابق إجمالي درج آخر وردية مع دفتر الأستاذ (استعلام واحد) قبل فتح البيع.

## 5. سيناريوهات الطوارئ

| الحادثة | الإجراء | ما يجب فحصه |
|---|---|---|
| الجلسة تنتهي باستمرار | تحقق من `/auth/refresh` في الخادم؛ الواجهة تتدهور إلى `/login` مع `returnTo` | سجل `401` المتكرر + `requestId` |
| فواتير مكررة | **أوقف البيع**؛ طابق `sales` مع الطلبات | هل الخادم يخزّن `Idempotency-Key` ويعيد نفس الاستجابة؟ (§16.4 من التدقيق) |
| فشل الطباعة | استخدم «نسخة الخادم» من حوار النجاح | مسار `receipt.printPayloadUrl`، وتعريف الطابعة 80mm |
| انقطاع متكرر للشبكة | البيع معطّل تلقائيًا؛ أعد الاتصال وأعد المحاولة بنفس السلة | السلة تُستعاد لنفس المستخدم خلال 30 دقيقة |
| شكوى «الفاتورة لا تطابق الإيصال» | راجع `GET /sales/:id` — الإيصال يعرض النسخة المحلية موسومة إن تعذّر جلب الخادم | `verified:false` في بيانات الإيصال |
| تسريب جلسة محتمل (XSS) | اعزل الجهاز، ألغِ جلسات المستخدم من الخادم، بدّل كلمات المرور | راجع `dangerouslySetInnerHTML` (موقعان فقط، كلاهما من بيانات مولّدة داخليًا) |

## 6. التراجع (Rollback)

1. أعد نشر الإصدار السابق من الواجهة (Vercel → Deployments → Rollback). الواجهة stateless.
2. امسح Service Worker للعملاء: ارفع `VERSION` في `public/sw.js` (يزيل الكاشات القديمة عند `activate`).
3. إن تغيّر عقد الـ API: أعد نشر الخادم أولًا واترك الواجهة متوافقة للخلف.

## 7. مراجعة أمنية سريعة (شهريًا)

```bash
npm audit --omit=dev --json | node scripts/audit-gate.mjs
node scripts/check-secrets.mjs
```

- راجع `.audit-allowlist.json`: أي استثناء انتهى تاريخه = فشل البناء.
- تأكد أن `NEXT_PUBLIC_*` لا يحوي أي سر (كل ما يبدأ بـ `NEXT_PUBLIC` يصل للمتصفح).
- تأكد أن الصلاحيات مفروضة في الـ API (اختبار 403 لكل دور)، لا في الواجهة.

## 8. اختبارات القبول المرتبطة

| الاختبار | الأمر | يحتاج |
|---|---|---|
| وحدة (منطق مالي/جلسة/CSV/شبكة) | `npm test` | لا شيء |
| عقد API | `CONTRACT_API_URL=... npm run test:contract` | staging |
| إعداد النشر + CORS | `npm run verify:deploy -- <fe> <api>` | بيئة منشورة |
| E2E | `E2E_BASE_URL=... npx playwright test` | staging + Chromium |
